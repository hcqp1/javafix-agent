# JavaFixAgent 持续聊天与任务恢复设计

**状态：已通过用户评审**

**日期：2026-10-27**

## 1. 背景

JavaFixAgent 当前通过一次性 CLI 启动：传入项目目录和一个 Bug 描述，`Main` 创建 `AgentLoop`，完成一次修复流程后退出。`AgentLoop` 的对话轨迹只存在于本次进程；`RunJournal` 会将单次运行过程追加到用户目录的 JSONL 文件，但下一次启动不会恢复该上下文。模型 URL、API Key 和模型名当前由环境变量提供。

用户希望先配置一次模型，随后在持续运行的 CLI 中连续交互；同一 Bug 的后续要求应能接续处理，切换到另一个 Bug 时不应把前一个 Bug 的上下文混入新任务；旧任务应保留，之后还可以重新打开。

## 2. 目标

1. 提供持续运行的 CLI 聊天入口，进程不再对应唯一一次修复。
2. 把每个独立 Bug 作为单独任务，分别保存对话、Agent 运行轨迹和任务状态。
3. 支持开始新任务、列出任务、切换项目、恢复旧任务和正常退出。
4. 用户重启程序后仍可恢复任务对话记录；异常退出时，已落盘的记录仍可读取。
5. 记录任务关联的代码工作区信息，并在恢复时检查工作区是否已变化，避免让旧上下文静默作用于意外的代码版本。
6. 支持用户目录配置文件保存模型配置；API Key 不进入仓库，也不要求每次启动或提问时重复输入。

## 3. 非目标

- 初版不支持多个 Agent 任务同时执行。
- 初版不自动创建 Git 分支或 worktree，不自动 checkout、reset、stash 或覆盖用户代码。
- 初版不实现 Web 前端、远程同步或跨机器会话同步。
- 初版不承诺精确恢复进程崩溃时正在进行的模型请求；只恢复已写入磁盘的会话和步骤记录。
- 初版不建立跨 Bug 的长期经验库；旧任务上下文只在显式恢复该任务时加载。

## 4. 设计原则

### 4.1 任务上下文隔离

一个 Bug 对应一个任务 ID。继续该 Bug 时，加载该任务自己的对话与运行记录；开始新 Bug 时创建全新上下文。切换任务不会删除任何旧记录，也不会将旧任务的完整对话带入新任务。

### 4.2 对话恢复不等于代码回滚

恢复任务会恢复对话、任务元数据和 Agent 已记录的运行轨迹，但不自动恢复项目文件。运行前检查任务记录的工作区身份和 Git 状态；如当前工作区与上次记录不同，向用户展示差异并要求明确选择继续使用当前工作区，或取消恢复。初版不提供自动切换到旧代码版本的行为。

任务会记录项目绝对路径、Git 仓库根目录（若有）、分支名、HEAD commit，以及创建/切换和每次任务结束时可获取的工作区状态摘要。非 Git 项目只记录规范化项目路径。工作区摘要用于提示变化，不作为完整代码快照，也不声称可以还原未提交文件。

### 4.3 持久化与敏感信息

配置与任务数据均保存在用户目录下的 `.javafix-agent` 中，不写入项目仓库。尽可能限制配置和会话文件的访问权限；Windows 下使用当前用户 ACL 的默认保护，并在文档中说明 API Key 文件仍由本机账户保护。日志不记录 API Key。

### 4.4 兼容现有运行轨迹

保留逐步追加、异常退出后仍可查看的记录方式。新的会话存储可复用 JSONL 事件思路，但应区分用户消息、Agent 运行事件、任务状态和会话元数据，避免将一次完整 Agent 运行误认为整段聊天。

## 5. 用户交互提案

### 5.1 启动与首次配置

- `javafix`（或项目当前 Maven 启动方式）进入 REPL。
- 若没有配置文件，提示配置模型服务 URL、模型名和 API Key，并写入用户目录配置文件；API Key 输入应不回显。
- 配置已存在时直接启动，不要求再次输入 Key。
- 环境变量可作为临时覆盖，优先级为：命令行明确覆盖（如支持）> 环境变量 > 用户配置文件。初版可不提供命令行 Key 参数，避免 Key 留在 shell 历史中。
- 配置文件损坏或缺少必要字段时，给出字段级说明并允许重新配置，不输出 Key 内容。

### 5.2 REPL 命令

| 命令 | 行为 |
|---|---|
| `/project <路径>` | 选择或切换当前项目。新项目不会自动沿用之前任务的对话。 |
| `/new <Bug 描述>` | 在当前项目下创建任务，初始化独立的 Agent 上下文并开始修复。 |
| `/tasks` | 列出任务 ID、标题、项目路径、更新时间和状态。 |
| `/resume <任务ID>` | 恢复一个已有任务；先检查记录项目与当前工作区状态，再继续交互。 |
| `/ask <问题>` | 对当前任务和项目进行只读代码问答，不启动自动修复阶段。 |
| `/fix <需求>` | 在当前任务中继续处理修复/修改请求。 |
| `/help` | 显示命令和状态说明。 |
| `/exit` | 正常退出；当前任务记录保留。 |

没有活动任务时，普通文本不直接触发修复，CLI 提示用户先运行 `/new` 或 `/resume`。有活动任务时，普通文本作为该任务的后续消息；CLI 应在每轮之前显示当前任务 ID 和项目，避免用户忘记上下文归属。`/ask` 与 `/fix` 的显式区分可以降低把代码咨询误当作自主修复的风险。

### 5.3 任务状态

- `ACTIVE`：当前会话正在处理。
- `PAUSED`：用户切换任务或退出时暂停；可恢复。
- `COMPLETED`：Agent 已返回结果，但任务记录仍可恢复和追问。
- `INTERRUPTED`：进程异常终止或未写入正常结束事件；允许恢复已落盘内容。

状态只用于展示与恢复流程，不代表修复正确性。测试通过与否仍由 Agent 的验证结果表达。

## 6. 持久化目录与数据模型

建议目录结构：

```text
~/.javafix-agent/
  config.json                 # baseUrl、apiKey、model
  tasks/
    <task-id>/
      task.json               # 标题、项目身份、状态、时间、Git 元数据
      events.jsonl            # 用户消息、Agent 事件、工具轨迹、状态变更
```

`task.json` 建议字段：

- `id`：随机、稳定且唯一的任务 ID。
- `title`：由首条 Bug 描述生成，可由用户改名（可后续实现）。
- `projectPath`：规范化后的项目路径。
- `repositoryRoot`、`branch`、`headCommit`：Git 项目可用时记录。
- `workspaceStatusDigest`：记录时工作区变更概况；不是可还原快照。
- `status`、`createdAt`、`updatedAt`、`lastRunId`。

`events.jsonl` 建议事件类型：

- `user_message`：用户输入、模式（`ask` 或 `fix`）、时间。
- `agent_run_started` / `agent_run_finished`：本轮 Agent 执行边界和结果状态。
- `agent_step`：沿用现有运行轨迹事件，记录阶段、模型动作、工具调用及观察结果。
- `task_status_changed`：任务状态变化。
- `workspace_observed`：开始、恢复、结束任务时观察到的项目/Git 状态。

单条事件追加成功后即持久化。读取时忽略文件末尾不完整的 JSON 行，并将任务标记为可恢复的 `INTERRUPTED`，不丢弃此前完整事件。模型 API Key 只能存在配置文件中，不复制到任务事件、错误消息或诊断输出。

## 7. 上下文恢复规则

1. 首次执行 `/new` 时，以 Bug 描述作为该任务初始请求，建立空白的任务级上下文。
2. 同一任务后续 `/ask` 或 `/fix` 消息只进入当前任务上下文。
3. `/new` 先把当前任务设为 `PAUSED`，再创建新任务；不清空或覆盖原任务事件。
4. `/resume` 按任务 ID 加载该任务自己的事件，不加载其他任务的对话。
5. 为控制上下文长度，可从事件存储重建最近对话并使用任务内摘要；摘要必须关联同一任务，不跨任务复用。初版先定义持久化完整事件，再决定上下文窗口裁剪策略。
6. 恢复后，Agent 应获知本次恢复的工作区检查结果；若工作区变更，用户确认前不得调用会修改文件或执行测试的修复工具。只读 `/ask` 是否允许在变更工作区继续，可由用户确认后决定。

## 8. 工作区与 Git 安全行为

- 对同一任务恢复时，若项目路径不可用或仓库身份不匹配，应中止 Agent 执行并提供修复路径。
- 若分支或 HEAD 与记录不一致，或工作区从干净变为有改动/反向变化，显示检测到的差异摘要；用户可以继续使用当前工作区，也可以取消恢复。JavaFixAgent 不替用户 checkout 或清理代码。
- 多个任务可以指向同一项目，但初版一次只允许一个任务处于活动状态。切换后，新任务仍使用用户当前选择的项目工作区，Agent 不会自动并发改写。
- 如果任务需要精确回到历史代码版本，用户可在 Git 中自行切换到对应状态后恢复会话。后续版本可评估每任务 worktree/分支；该能力不纳入本次初版。

## 9. 候选方案比较

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| 所有 Bug 共用一个持续上下文 | 交互最简单 | 旧 Bug 信息污染新任务；无法可靠恢复某次修复 | 不采用 |
| 每个 Bug 独立任务记录，恢复时检查工作区，但不自动回滚 | 任务隔离、实现复杂度适中、不擅自更改用户代码 | 恢复对话不保证恢复代码；需要提示工作区变化 | **建议作为初版** |
| 每个 Bug 自动建 Git worktree 并绑定任务 | 对话和代码版本隔离明确，利于并行 | 要处理非 Git 项目、未提交改动、分支冲突、worktree 清理及 Windows 路径等；初版范围明显变大 | 作为后续增强 |

## 10. 验收标准

1. 首次配置后，退出并重新启动 CLI，不重新输入 API Key 即可使用模型；Key 不出现在控制台明文、任务记录或 Git 仓库中。
2. 连续在同一任务中追问时，Agent 可看到该任务之前的用户消息和已完成步骤。
3. 创建第二个 Bug 后，新任务的上下文不含第一个 Bug 的对话；第一个任务仍出现在 `/tasks` 中。
4. 恢复第一个任务后，其消息和轨迹可读，第二个任务消息不进入其上下文。
5. 异常退出后，完整事件仍可读；文件末尾不完整事件不会破坏前面的记录。
6. 恢复任务时发现项目路径、Git HEAD 或工作区状态变化，会先提示并取得用户选择；未经选择不得执行修改工具。
7. `/ask` 走只读流程，`/fix` 才进入可修改代码的 Agent 流程；没有活动任务时普通输入会得到清晰提示。
8. 初版没有自动 checkout、reset、stash、删除任务记录或并行执行行为。

## 11. 待用户评审的重点

1. 是否接受初版“任务对话可恢复，但代码不自动回滚；检测到工作区变化时由用户决定继续或取消”的边界？
2. 是否接受将 `/ask`（只读问答）与 `/fix`（修复请求）显式区分？
3. 任务记录是否默认永久保留，还是需要一个明确的 `/delete <任务ID>` 命令？本提案默认保留，不提供删除命令，避免误删。
4. 用户目录配置文件保存 API Key 是否满足预期？如需更强保护，可后续接入 Windows Credential Manager / macOS Keychain / Linux Secret Service。

只有用户审批此设计后，才进入实现计划与开发阶段。
